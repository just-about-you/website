Checking

Do not take our word for any of it.

Anyone can say their app is private. This page lists every claim we make, what implements it, and what stops it quietly becoming false. The last section is the claims that have no test yet.

Why a claim needs a test

Every claim below has been true, and has stopped being true, at least once in this project’s history. That is not unusual — it is what happens to any promise nobody checks. The difference is whether something fails when it happens.

The claims

No reading value is stored on our server

Blood pressure, blood sugar, oxygen, heart rate, sleep, weight, water — none of these has a column on our side. By default what a caregiver can see is a tick against a category and a date. Two things go further and both need you to act: a single reading you approve when they ask, and any medication you tag for them.

Where: The table that records sharing holds four things: a random code, a date, a category, and yes-or-no. There is nowhere for a number to go.

What keeps it true: A test fails the build if a forbidden column name appears in the table definitions or in a query.

No name of any kind is stored

Not your real one and not a chosen one. What you call the people you know is written on your phone and never sent.

Where: Neither the people table nor the care links have a name column, and the app sends none when it registers.

What keeps it true: A test asserts the registration request carries the random code alone.

The words of a shared task are unreadable to us

A task you share is encrypted on your phone before it leaves, with a key sealed to each person in it.

Where: One key per task, sealed separately to every participant. We store what comes out and cannot open it.

What keeps it true: A test seals with the real cipher, opens with the real device key, and asserts the text cannot be recovered without it — with a control that proves the test can fail.

A reading someone sends you is never written down

If you approve a request for one number, that number reaches the person who asked and is then gone. It is not saved on either phone.

Where: It lives in memory that dies with the app. The modules that hold it do not import the database, the preferences store, the files it keeps on disk, or the file system at all.

What keeps it true: One test asserts those imports stay absent. A second searches the raw bytes of a produced backup for the value, with a control.

Turning a category off removes the days it already shared

Sharing is about now. Switch something off and its past days go with it — they are deleted, not hidden.

Where: History is filtered by what is shared today, and the stored rows are removed.

What keeps it true: A server test covers it.

A day with no record is not a missed day

Someone who installed the app last week is not shown as having ignored it for a month.

Where: The count of missed days starts at a person’s earliest record rather than at the beginning of time.

What keeps it true: A server test covers exactly the newcomer case. Before it existed, a new account was shown as having missed thirty days.

The privacy words in the app match what the app does

The text you read inside the app is held to the code by tests, not by anyone remembering to update it.

Where: Four separate guards: one for coverage per feature, one that fails the build when a new category or table appears, and two for specific claims.

What keeps it true: Four guards on wording looks excessive until you know that shipped privacy text in this project has been falsified by its own code three separate times.

A category you have not shared is never uploaded

Not uploaded and then filtered — never sent. A phone with nobody looking after it sends nothing at all.

Where: The upload is filtered by the shared set before it is built.

What keeps it true: A server test, plus assertions on the wiring in the app. Those are checked at source level on purpose: the obvious behavioural test passed with the gate deleted.

An installed app was built with its real server address

A release built without its settings compiles a placeholder address, installs perfectly, and can reach nothing.

Where: A tool opens the built file and counts the expected address inside it.

What keeps it true: Not a test — a tool, run at release time. Every build handed over before August 2026 had this wrong and nothing said so.

Claims with no test yet

Listed because a gap you can see is worth more than one you cannot. Each of these is true; none of them has something that would fail if it stopped being true.

9 claims mapped to the code that implements them
3 with no test yet — named below, not buried
0 readings, of anyone, in our database — one can sit encrypted in the hand-over store between approval and pickup, which is the third card below

The database on your phone is encrypted at rest

True, and exercised by every test that touches it — but nothing asserts that the file on disk is unreadable without the key. That needs a real phone and a rooted read.

The backup hint is stored as plain text inside the file

True and intended, and the app warns you about it. Nothing tests that the warning is read.

A reading in transit is deleted when it is picked up

Covered by a server test behaviourally, but nothing proves the bytes are gone from the disk underneath.

Running them yourself

The tests are in the source, not behind a login. The app’s run on any machine with Flutter installed; the server’s run inside its own container.
